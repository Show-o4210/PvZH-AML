# 测试卡表触发牌组清理

R66 RC1 第一次在设备主用户部署独立测试卡表时，牌组保护清理了两个牌组文件和一个库存文件中的镜像卡引用。开发目标原本只是在离线战斗里观察调色副本。部署把整张卡表作为一个资源族替换，此前牌组和库存中的一些卡牌引用失去了有效定义。

## 复盘

1. 测试样本能定义要出场的新卡，仍需检查部署后完整卡表能否解释该用户已有的卡牌引用。R66 的旧组合已有镜像卡，独立测试卡表省略了那些定义。离线模式下，启动准备仍会检查本地牌组和库存。
2. 首轮事务记录了受影响的 `PlayerDecks`、`PlayerDecksDelta` 和 `PlayerInventory`，三个文件的暂存指纹均与部署前不同。通过该次事务留下的前像恢复，并核对 SHA256、所有者、权限和 SELinux 类型。恢复范围限定于这三份受影响的文件。
3. 恢复旧资源组合后，从原来生效的卡表构造两个后续验收包。两个候选各自保留原有 **1,169 个卡牌定义及身份**，再加入测试所需的新卡。后续两次离线对局部署均未触发玩家文件清理。测试结束恢复原组合与设置，验收记录确认受检玩家文件指纹与首轮操作前一致。

## 下次怎样验证

- 用隔离测试用户和合成数据复现。先解析此次活动 Manifest 和 Mod 顺序，确定最终生效的 `cards/card_data`。核对每个既有 GUID 仍指向同一个卡牌身份，检查新增测试卡是否碰号。多个 Mod 带卡表时，要按实际整文件覆盖结果检查。
- 在隔离数据中准备一条引用旧卡的牌组和库存记录。用仅含原版加少量新卡的测试卡表复现缺项，再用保留既有定义的候选复测。分别记录启动准备报告中的受影响文件和清理数量、实际文件指纹、游戏中是否看见目标卡。预期无数据改动的用例应核对清理数量为零。
- 如果出现意外写入，先停止后续启动和覆盖。将当前文件的指纹与事务记录的写入后指纹比较，再核对可恢复前像。当前文件已被下一次操作改变时，保留现场供人工判断。R66 此处复盘的是一次已经验证的逐文件恢复。

工作区 R66 RC1 的 `evidence/cactus-device.json` 记录首轮事务的修改、恢复以及后续部署。美术验证和版本边界见[整卡调色的依赖排查](README.md)。
